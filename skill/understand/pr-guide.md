# PR（変更）を理解するための説明文書の作り方

目的は、ユーザーが**PRの全体像をつかみ、細部は寄り道で掘れる状態**にすること。
レビューの指摘をすることではない（聞かれていなければ、良し悪しの評価は書かない）。

## 1. 対象を特定する

依頼文に番号やブランチ名があればそれを使う。なければ今のブランチのPRを対象にする。

```bash
# GitHubのPR（gh が使える場合）
gh pr view <番号 or 空> --json number,title,body,author,baseRefName,headRefName,additions,deletions,changedFiles,files,commits
gh pr diff <番号 or 空>
```

`gh` が使えない、またはPRがまだない場合は、ブランチの差分で代わりにする。

```bash
git rev-parse --abbrev-ref HEAD
BASE=$(git merge-base HEAD origin/main 2>/dev/null || git merge-base HEAD main)
git log --oneline "$BASE"..HEAD
git diff --stat "$BASE"...HEAD
git diff "$BASE"...HEAD
```

差分が大きいときは、`--stat` で全体を見てから、主要なファイルだけ中身を読む。
変更の意図をつかむために、必要なら変更後のファイル全体や、呼び出し元も読む。

## 2. 説明文書の構成

`<DIR>/main.md` に、次の構成で書く。見出しは変えてよいが、順番（全体→部分）は守る。

```markdown
# <PRのタイトル>（#番号）

## 一言でいうと
何を・なぜ変えるPRかを2文以内で。

## 背景
なぜこの変更が必要になったか。PRの説明文・コミットメッセージ・関連コードから読み取れる範囲で。
読み取れないことは「PRからは読み取れない」と書き、推測で埋めない。

## 変更の全体像
変更を「まとまり」ごとに3〜5個に分けて、番号付きで並べる（ファイル単位ではなく意味の単位）。
各まとまりは、見出し＋何が変わるか＋なぜ、を2〜4文で。
処理やデータの流れが変わるなら、```mermaid の図を1つ入れる。

## 主な変更の中身
上のまとまりのうち、理解に欠かせないものだけ、コードを抜粋して説明する。
- 1つの抜粋は15行以内。全体の差分を貼らない。
- 抜粋の前に「何を見てほしいか」を一文で書く。
- 抜粋は必ずコマンドの出力からそのまま写す（記憶や要約で書き直さない）。
  変更後のコード：sed -n '<開始>,<終了>p' <ファイル> で取り、見出し行は「~~~~言語名 ファイルパス:開始行」
  差分そのもの：gh pr diff / git diff の該当部分を取り、見出し行は「~~~~diff ファイルパス」

## 読むときのポイント
影響範囲、前提にしている仕様、テストで確かめていること、まだ決まっていないこと などを箇条書きで3〜5個。

## 変更ファイル
| ファイル | 変更の内容 | 増減 |
（--stat の数字を使う。10ファイルを超えたら主要なものだけ載せ、残りは「ほかN件」）
```

## 3. 書き方のルール

- ユーザーは読みながら、わからない文を選んで質問する。**一文に一つのことだけ**を書き、用語は最初に出たところで短く説明する。
- 関数名・ファイル名は `バッククォート` で囲む。
- コードの抜粋はアプリで行番号付きで表示される。見出し行の「ファイルパス:開始行」が実際と合っていることを確かめる。
- 長さの目安は、抜粋を除いて画面2〜3枚分。細部はユーザーが寄り道で掘るので、全部を書こうとしない。
- `title.txt` には PRのタイトルを短くしたものを書く。
