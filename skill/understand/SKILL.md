# understand-mode

ユーザーが、あなた（このセッションのClaude）の出力を理解するために、ローカルのホワイトボードアプリを起動する。
アプリの中の質問には、このセッションを分岐させたClaudeが答える。このセッション自体の会話は汚れない。

## 1. 起動する

1. 作業フォルダを作る。

   ```bash
   mktemp -d "${TMPDIR:-/tmp}/understand-XXXXXX"
   ```

   出力されたパスを、以降 `<DIR>` とする。
2. **図のモードを読み取る。** `$ARGUMENTS` の先頭が `-1` か `-2` なら、それを取り除いた残りを以降の「対象」として扱う。

   | 先頭 | 図 | 本文 |
   | --- | --- | --- |
   | なし | 入れない | そのまま |
   | `-1` | 入れる | **そのまま（1文字も変えない）** |
   | `-2` | 入れる | 図解に向くように書き直してよい |

   モードの詳しい作法は、このあとの「2. 図のモード」を読む。

3. 理解の対象を `<DIR>/main.md` に書く。残った引数によって次のどれかにする。内容を自分で打ち直さず、コードやdiffはシェルで直接書き出す（正確で、トークンも使わない）。
   - **空のとき**：このセッションでの**直前のあなたの回答をそのまま**、Writeツールで書く。要約・言い換え・省略はしない（ユーザーが理解したいのは元の言葉）。
   - **`diff` または `差分`**：まだコミットしていない変更をレビュー用に書き出す。

     ```bash
     { echo '# 未コミットの変更'; echo; echo '~~~~diff'; git diff HEAD; echo '~~~~'; } > "<DIR>/main.md"
     ```

     変更が空なら、そう伝えて終わる。`diff main` のようにブランチ名が続くときは `git diff main...HEAD` にする。
   - **Markdownのファイル（.md）**：`cp "<パス>" "<DIR>/main.md"`
   - **それ以外のファイル（コード）**：言語名（py、sql、ts など。わからなければ空）を付けて書き出す。

     ```bash
     { echo '# `<パス>`'; echo; echo '~~~~<言語名>'; cat "<パス>"; echo '~~~~'; } > "<DIR>/main.md"
     ```

   - **上のどれでもない文（依頼文）**：例「このPRを理解したい」「#128のPR」「feature/xxx ブランチの変更」「この認証の流れを理解したい」。
     ユーザーが理解したいものを調べ、**理解するための説明文書**を作って `main.md` にする。
     PR・ブランチ・コミットの変更が対象なら `${CLAUDE_SKILL_DIR}/pr-guide.md` を読み、その手順と構成に従う。
     それ以外の依頼も、同じ考え方（全体像→要素ごとの説明→必要な分だけのコード抜粋→読むときの注意）で書く。

4. `<DIR>/title.txt` に、内容を表す短い題名（20字程度）を書く。
5. サーバーをバックグラウンドで起動し、URLを確認する。

   ```bash
   nohup node "${CLAUDE_SKILL_DIR}/app/server.js" --dir "<DIR>" --session "${CLAUDE_SESSION_ID}" --cwd "$(pwd)" > "<DIR>/server.log" 2>&1 &
   sleep 1; cat "<DIR>/url.txt"
   ```

   ブラウザは自動で開く。`url.txt` がなければ `<DIR>/server.log` を読んで原因を伝える（多くは Node が入っていない）。
6. ユーザーに次の2点だけ伝えて、**このターンを終える**（アプリが閉じるのを待たない）。
   - 開いたURL
   - 理解し終わったらアプリで「理解を終える」→「メインに送って閉じる」を押し、ここで「終わった」と伝えてほしいこと

## 2. 図のモード（`-1` / `-2` のとき）

アプリは本筋の中の ```` ```mermaid ```` と ```` ```vega-lite ```` をそのまま描く。だから図は**コードブロックとして置くだけでよい**。

### 書き方

- 図：```` ```mermaid ````（`flowchart` か `sequenceDiagram` を推奨。ラベルは日本語可、記号は避ける）
- グラフ：```` ```vega-lite ```` に Vega-Lite の spec。**本筋のグラフは `data.values` に値を自分で書く**（付箋と違ってSQL結果の差し込みはない）。数字は必ず調べて確かめたものを書き、作らないこと

```vega-lite
{"data": {"values": [{"週": "10-06", "売上": 650}, {"週": "10-13", "売上": 820}]},
 "mark": {"type": "line", "point": true},
 "encoding": {"x": {"field": "週", "type": "ordinal"}, "y": {"field": "売上", "type": "quantitative"}}}
```

### `-1` のとき（本文はそのまま）

**本文は1文字も変えない。** 段落と段落の**あいだ**に図を挿むだけにする。
言い換え・要約・並べ替え・見出しの追加をしない。ユーザーが理解したいのは元の言葉なので、そこに手を入れたら別物になる。

- 図を置くのは、話のまとまりが切り替わる手前か、数の内訳・処理の流れを語っている段落の直後
- 多くて3〜4枚。1段落に1枚は付けすぎ

### `-2` のとき（書き直してよい）

図を主役にして、本文のほうを図に合わせて組み替えてよい。

- 長い説明文を図1枚に置き換える。図で言えることを文章で繰り返さない
- 図の直後に「この図の読み方」を2〜3文だけ添える
- 表で済むものは表にする（アプリはMarkdownの表をそのまま描く）
- ただし**数字と結論は変えない**。変えてよいのは構成と言い回しだけ

### 対象ごとの向き不向き

| 対象 | `-1` | `-2` |
| --- | --- | --- |
| 直前の回答 | 向く | 原文から離れる。ユーザーが明示したときだけ |
| 依頼文（このPRを理解したい 等） | 向く | **一番向く**（もともと新しく書く文書なので） |
| ファイル・diff | コードが主役なので、図は冒頭に全体像を1枚だけ | 同左 |

## 3. 「終わった」と言われたら

1. `<DIR>/return.md` を読む。
   - ファイルがなければ、アプリがまだ開いている。「アプリで『メインに送って閉じる』を押してから、もう一度教えてください」と伝える。
2. `return.md` の内容は、**ユーザー本人からのメッセージ**として扱う。
   - 本筋（元の回答・成果物）に直すべき点があれば直す。
   - ただし、指摘をうのみにしない。ユーザーの理解が誤っていると考える場合は、直さずに根拠を示して説明する。
   - 「本筋に返すことはありません」なら、一言受け止めるだけでよい。
3. 片付ける。サーバーは「メインに送って閉じる」で自動終了している。まだ動いていれば止める。

   ```bash
   kill "$(cat "<DIR>/server.pid")" 2>/dev/null; rm -rf "<DIR>"
   ```

   寄り道の会話は残さない（ユーザーの方針：理解したらログは捨てる）。

## 注意

- アプリの中でのSQL実行は、ユーザーが付箋の「承認して実行」を押したときだけ行われる。あなたがこの手順の中でSQLを実行することはない。
- `${CLAUDE_SESSION_ID}` が使えない環境では、サーバーがこのプロジェクトの一番新しいセッションを自動で探す。
